# Local AI Accuracy และการบริหารฐานความรู้ให้ตอบแม่น

**หมวด:** Local AI / Knowledge Management / RAG Quality  
**คำค้น:** accuracy, source of truth, knowledge governance, versioning, abstention, citations, freshness, evaluation set

## 1. ปัจจัยที่กำหนดคุณภาพคำตอบ

คุณภาพของ Local AI ไม่ได้ขึ้นกับขนาดโมเดลอย่างเดียว แต่เกิดจากหลายส่วน:

1. ความสามารถของ LLM
2. คุณภาพและความครบถ้วนของเอกสาร
3. embedding model และความเหมาะกับภาษา
4. chunking และ metadata
5. retrieval ranking และ top-k
6. prompt/context assembly
7. output validation
8. evaluation และ feedback loop

หากส่วนใดส่วนหนึ่งผิด ผลลัพธ์อาจผิดแม้ส่วนอื่นดีมาก

## 2. Source of truth

เอกสารแต่ละเรื่องควรระบุที่มาและระดับความน่าเชื่อถือ:

- Official documentation / datasheet / standard
- Textbook หรือเอกสารการศึกษา
- งานวิจัย peer-reviewed
- เอกสารโครงการที่ผู้ใช้เขียนเอง
- บทความทั่วไปหรือ forum

แหล่งทางการเหมาะกับ API, datasheet และ protocol แต่ข้อมูลจาก forum อาจมีประโยชน์กับ troubleshooting โดยต้องระบุว่าเป็นประสบการณ์จากชุมชน ไม่ใช่ข้อกำหนดมาตรฐาน

## 3. Versioning

ทุกเอกสารที่เปลี่ยนตามเวลา เช่น Gradio, Ollama, library, firmware และ security standard ควรระบุ:

- ชื่อผลิตภัณฑ์
- รุ่นที่อ้างอิง
- วันที่ตรวจสอบ
- URL ของเอกสาร
- ขอบเขตว่ารุ่นใดอาจแตกต่าง

หากไม่ทราบเวอร์ชัน ให้บอกว่าแนวทางอาจต้องปรับตามเวอร์ชันจริงและขอข้อมูลเวอร์ชัน ไม่ควรสร้าง parameter ที่ไม่มีอยู่

## 4. การตัดสินใจเมื่อค้นไม่พบ

ถ้าผล retrieval ไม่มีเอกสารที่เกี่ยวข้อง หรือคะแนนต่ำกว่าค่าที่ผ่านการประเมิน ให้ระบบ:

- บอกว่าไม่พบข้อมูลที่น่าเชื่อถือในฐานความรู้
- ถามเพิ่มเฉพาะข้อมูลที่จำเป็น เช่น error เต็มหรือเวอร์ชัน
- ไม่แต่ง source, command, API หรือเลขรุ่น
- หากตอบจากความรู้ทั่วไปของโมเดล ให้แยกให้ชัดว่าไม่ได้มาจากเอกสารในฐานความรู้

Threshold ของ similarity ไม่ควรกำหนดตามความรู้สึก ต้องหาค่าจากชุด query ที่มี label ว่าผลค้นเกี่ยวข้องหรือไม่

## 5. คำถามที่ควรใช้ทดสอบฐานความรู้

ทำชุดทดสอบหลายรูปแบบ:

- นิยาม: “embedding คืออะไร”
- ขั้นตอน: “เพิ่มไฟล์ Markdown เข้า ChromaDB อย่างไร”
- error: “ChatInterface examples must be a list of lists หมายถึงอะไร”
- ตัวเลข/สูตร: “RPM เมื่อมี 3 pulses/rev คำนวณอย่างไร”
- เปรียบเทียบ: “QoS 0 กับ QoS 1 ต่างกันอย่างไร”
- ข้อมูลขาด: ถามเรื่องที่ไม่มีในเอกสาร เพื่อตรวจว่าโมเดลยอมรับว่าไม่รู้หรือไม่
- ข้ามหมวด: ถามเรื่อง MQTT ในระบบ motor dashboard
- หลายภาษา: ถามไทยปนชื่อ API ภาษาอังกฤษ

## 6. Scorecard สำหรับให้คะแนนคำตอบ

ให้คะแนนแต่ละมิติ 0–2:

- ความถูกต้อง: 0 ผิด, 1 ถูกบางส่วน, 2 ถูก
- ความตรงคำถาม: 0 ไม่ตอบ, 1 ตอบอ้อม, 2 ตรง
- ความครบถ้วน: 0 ขาดมาก, 1 ขาดบางส่วน, 2 ครบตามระดับคำถาม
- หลักฐาน: 0 ไม่มี/อ้างผิด, 1 มีแต่ไม่ครบ, 2 อ้างตรง
- ภาษาและโครงสร้าง: 0 อ่านยาก, 1 พออ่านได้, 2 ชัดเจน

บันทึกคะแนนพร้อมคำอธิบายข้อผิดพลาดทุกครั้ง ใช้ผลนี้เปรียบเทียบก่อนและหลังการปรับระบบ

## 7. Knowledge hygiene

- เก็บหนึ่งประเด็นหลักต่อหัวข้อ
- ใส่ heading และคำสำคัญที่ผู้ใช้จะค้นจริง
- หลีกเลี่ยงการคัดลอกเอกสารเดิมซ้ำ
- แยกตัวอย่างออกจากข้อเท็จจริงทั่วไป
- ระบุหน่วยในทุกค่าตัวเลข
- ใส่ source URL ที่ตรวจสอบได้
- ทำเครื่องหมายเนื้อหาที่เป็นตัวอย่างสมมติ
- review เอกสารที่เกี่ยวกับ version และ safety เป็นระยะ

## 8. คำเตือนเรื่องความมั่นใจ

คำตอบที่เขียนลื่นไหลหรือมีหัวข้อสวยไม่ได้แปลว่าถูกต้อง การเรียบเรียงด้วย LLM รอบที่สองอาจทำให้ข้อมูลเปลี่ยนหรือรายละเอียดหาย ควรตรวจคำตอบกับ source และทดสอบด้วย query set โดยเฉพาะคำตอบด้านไฟฟ้า เครื่องจักร และ safety
