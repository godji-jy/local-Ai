# Data Engineering และ Data Quality สำหรับ AI/ML

**หมวด:** Data Science / Database / RAG  
**คำค้น:** data cleaning, missing values, duplicates, schema, ETL, data validation, normalization, data lineage

## 1. ข้อมูลที่ดีสำคัญกว่าเพิ่มปริมาณข้อมูลอย่างเดียว

ข้อมูลจำนวนมากไม่ได้รับประกันคำตอบที่ถูกต้อง หากข้อมูลซ้ำ ขัดแย้ง ล้าสมัย หรือไม่มีบริบท โมเดลอาจดึงชิ้นส่วนผิดมาใช้ได้ เป้าหมายคือข้อมูลที่เกี่ยวข้อง ถูกต้อง มีที่มา และแบ่งเป็นหน่วยที่ค้นคืนได้

## 2. กระบวนการ ETL/ELT

- **Extract:** ดึงข้อมูลจาก Markdown, CSV, JSON, PDF หรือฐานข้อมูล
- **Transform:** แก้ encoding, ตรวจค่าว่าง, ทำรูปแบบให้สม่ำเสมอ, แยกหัวข้อ, ตรวจข้อมูลซ้ำ
- **Load:** บันทึกลงฐานข้อมูลหรือ vector store พร้อม metadata

เก็บไฟล์ต้นฉบับแยกจากข้อมูลที่ผ่านการแปลงเสมอ เพื่อให้ย้อนกลับไปตรวจสอบได้

## 3. Data profiling ก่อนนำเข้าระบบ

ตรวจอย่างน้อย:

- จำนวนไฟล์และจำนวนรายการ
- encoding และนามสกุลไฟล์
- จำนวนตัวอักษรหรือ token โดยประมาณ
- รายการว่างและรายการซ้ำ
- วันที่แก้ไขและเวอร์ชันเอกสาร
- หัวข้อที่ไม่มีเนื้อหา
- เนื้อหาที่มีแต่โค้ดหรือมีแต่ข้อความ

สร้างรายงานก่อน ingest เพื่อให้รู้ว่าข้อมูลถูกอ่านครบหรือไม่

## 4. Missing values และข้อมูลผิดรูปแบบ

อย่าเติมข้อมูลที่หายไปด้วยการเดา วิธีจัดการขึ้นกับความหมายของ field:

- ค่าที่หายเพราะไม่มีการวัด: เก็บเป็น null และระบุเหตุผล
- ค่าที่หายเพราะระบบล้มเหลว: จัดเป็น sensor/data-quality fault ไม่ใช่ค่าปกติ
- ค่าที่มีหน่วยต่างกัน: แปลงเป็นหน่วยมาตรฐาน พร้อมเก็บหน่วยเดิมหากจำเป็น
- timestamp: ระบุ timezone และรูปแบบอย่างชัดเจน

ตัวอย่าง sensor ที่อ่านค่า `-127 °C` จาก DS18B20 อาจหมายถึงสถานะอ่านเซนเซอร์ผิดพลาดในไลบรารี/การต่อวงจรที่ใช้ ไม่ควรนำไปคำนวณค่าเฉลี่ยอุณหภูมิเสมือนเป็นค่าจริง ต้องตรวจคู่มือไลบรารีและสถานะอุปกรณ์ก่อน

## 5. Data schema และ metadata

สำหรับ knowledge document ให้เก็บ metadata เช่น:

```json
{
  "source": "12_Data_Engineering_and_Data_Quality.md",
  "title": "Data Engineering และ Data Quality",
  "topic": "data_quality",
  "language": "th",
  "version": "1.0",
  "updated_at": "2026-10-30",
  "section": "Missing values",
  "chunk_id": "data-quality-004"
}
```

metadata ควรเป็น scalar ที่ระบบจัดเก็บรองรับ และใช้ชื่อ field สม่ำเสมอ อย่าใส่ข้อมูลส่วนตัวหรือ secret ลง metadata

## 6. Data lineage และ reproducibility

บันทึกว่า chunk มาจากไฟล์ไหน หัวข้อใด เวอร์ชันใด และถูกสร้างด้วยขั้นตอน ingest รุ่นไหน เมื่อแก้ไฟล์ ให้รู้ว่าต้องลบหรือแทน chunk เก่าชุดใด ไม่ควร append ทุกครั้งโดยไม่ตรวจ duplicate เพราะฐานความรู้อาจมีข้อมูลเก่าซ้ำหลายชุด

## 7. การจัดการข้อมูลซ้ำและขัดแย้ง

- ใช้ hash ของเนื้อหาเพื่อตรวจไฟล์หรือ chunk ที่เหมือนกัน
- ข้อมูลเดียวกันแต่ต่างเวอร์ชัน ให้เก็บ version และสถานะ current/deprecated
- ข้อเท็จจริงขัดแย้งกัน ให้เก็บแหล่งที่มา วันที่ และคำอธิบาย ไม่ควรเลือกคำตอบเองโดยไม่มีหลักฐาน
- เอกสารเก่าเกี่ยวกับเวอร์ชันซอฟต์แวร์ต้องระบุ version scope

## 8. Data validation ก่อน ingest

ตัวอย่างกฎ:

- ไฟล์ Markdown ต้องมี heading หลัก
- chunk ต้องไม่ว่าง
- source ต้องไม่ว่าง
- chunk ต้องมีความยาวไม่เกินขนาดที่กำหนด
- ไม่ ingest ไฟล์ชั่วคราวหรือไฟล์ backup ซ้ำ
- โค้ดใน fenced block ต้องไม่ถูกตัดกลางบรรทัดโดยไม่ตั้งใจ

## 9. อย่าสับสนระหว่างข้อมูลฝึกกับข้อมูลค้นคืน

Knowledge base แบบ RAG ไม่ใช่การฝึกโมเดลใหม่ แต่เป็นการจัดเก็บเอกสารและค้นบางส่วนมาแนบกับ prompt ในเวลาตอบ จึงแก้หรือเพิ่มความรู้ได้โดย ingest ใหม่ แต่ไม่ได้เปลี่ยน weights ของโมเดล
